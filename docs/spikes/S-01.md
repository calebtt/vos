# S-01 — avbroot `--rootless --replace product` on the GrapheneOS OTA (#11)

**Needed by:** M0 decision (M0-04, #129). **Device:** Phone B (Pixel 7 `panther`) default smoke; the same recipe must build for `akita` (Phone A path). Plan: TARGET-PLAN §6.0, §4.4, §8 (Mon 10-19).

## Claim
avbroot `--rootless --replace product` on the current **GrapheneOS** panther OTA, with a hello priv-app that requests `MODIFY_AUDIO_ROUTING`, `CAPTURE_AUDIO_OUTPUT`, `CAPTURE_VOICE_COMMUNICATION_OUTPUT`, `BYPASS_CONCURRENT_RECORD_AUDIO_RESTRICTION` (the plan's `CONCURRENT_AUDIO_RECORD_BYPASS` does not exist; see the correction below) and `MEDIA_CONTENT_CONTROL`, boots and relocks with the owner's `avb_custom_key`.

## Procedure (Caleb, on the workstation and Phone B; not run by CI or agents)

Steps 1–3 run on the desktop and need no phone. Steps 4–8 need Caleb's hands: the unlock and the lock each need a button press on the phone, and **each one wipes Phone B**. The commands follow avbroot 3.37.0's "Initial setup" and "Updates" sections.

1. **Owner keys, once:** `image/keys.sh` (prompts for two new passphrases; writes `~/.vos-keys/{avb.key,avb_pkmd.bin,ota.key,ota.crt}`). Store the passphrases in the password manager and copy `~/.vos-keys` to the offline USB stick before step 4.
2. **Hello APK** (package `com.vos.hello`, no code; requests `MODIFY_AUDIO_ROUTING`, `CAPTURE_AUDIO_OUTPUT`, `CAPTURE_VOICE_COMMUNICATION_OUTPUT`, `BYPASS_CONCURRENT_RECORD_AUDIO_RESTRICTION`, `MEDIA_CONTENT_CONTROL`). It is relocked on Phone B, so it is a release build, not debuggable, signed with a throwaway key that is deleted right after; nothing can later be installed over the baked copy. `image/build.sh` refuses debuggable or debug-key-signed APKs.

   ```bash
   key="$(mktemp -d)"
   eval "$(ci/make-throwaway-release-key.sh "$key" | sed 's/^/export /')"
   ./gradlew -p spikes/probes :probe-s01-hello:assembleRelease
   unset VOS_RELEASE_STORE_FILE VOS_RELEASE_STORE_PASSWORD VOS_RELEASE_KEY_ALIAS VOS_RELEASE_KEY_PASSWORD
   rm -rf "$key"
   ```

3. **Image:** build from the Graphene OTA that matches the phone's build. On the workstation, `VOS_IMAGE_OUT` points at the image directory on the data disk (§7); without it the image goes to `out/images/` in the checkout.

   ```bash
   build="$(adb shell getprop ro.build.version.incremental | tr -d '\r')"   # 2026101601 on 2026-10-20
   image/build.sh --device panther \
     --ota "/media/caleb/data-disk/vos/firmware/panther/grapheneos/$build/panther-ota_update-$build.zip" \
     --overlay image/overlays/s01-hello \
     --add priv-app/VosHello/VosHello.apk=spikes/probes/probe-s01-hello/build/outputs/apk/release/probe-s01-hello-release.apk
   vos_ota="$(ls -t "${VOS_IMAGE_OUT:-out/images}"/*/vos-panther-"$build"-s01-hello-*.zip | head -1)"   # the image just built
   ```

   It verifies the input against `image/pins/`, adds the overlay to `product` (`/product/priv-app/VosHello/VosHello.apk`, `/product/etc/permissions/privapp-permissions-vos-hello.xml`), re-signs with `~/.vos-keys`, verifies the output against the owner keys, and writes the zip plus a `.manifest.txt`. Details: `image/README.md`.
4. **Before the wipe:** move everything Phone B holds that a wipe would lose (see Result, "Phone B is not empty"), then `adb pull` what is left to `/media/caleb/data-disk/vos/backup/phones/panther/$(date +%F)/`. Check that the bootloader and radio already match the build: `fastboot flashall` below does not update them.

   ```bash
   adb shell getprop ro.bootloader            # cloudripper-17.0-15902555 for 2026101601 (matched 2026-10-20)
   adb shell getprop gsm.version.baseband     # g5300q-260604-260807-B-16036236 for 2026101601 (matched 2026-10-20)
   ```

   If either differs from the factory image of `$build` (`bootloader-panther-*.img`, `radio-panther-*.img` in `panther-install-$build.zip`), sideload the patched OTA once after step 5's first boot, as in step 8, before the relock.
5. **Unlock and flash.** fastboot must be version 35 or newer (`fastboot --version`; 37.0.1 on the workstation).

   ```bash
   adb reboot bootloader
   fastboot flashing unlock      # confirm on the phone (volume keys, then power); WIPES Phone B
   # Wait until the phone shows Fastboot Mode again before going on. If it boots into Android
   # instead, power it off and hold Volume Down + Power.
   fastboot getvar unlocked      # expect: unlocked: yes
   flash="$(mktemp -d)"
   avbroot ota extract --input "$vos_ota" --directory "$flash" --fastboot
   ANDROID_PRODUCT_OUT="$flash" fastboot flashall --skip-reboot    # ends in fastbootd
   fastboot reboot-bootloader    # avb_custom_key can only be written from the bootloader, not fastbootd
   fastboot erase avb_custom_key
   fastboot flash avb_custom_key ~/.vos-keys/avb_pkmd.bin
   fastboot reboot               # first boot, still unlocked (orange warning screen)
   ```

6. **Check grants** on that first, unlocked boot (minimal setup, USB debugging on): `adb shell dumpsys package com.vos.hello | grep -A8 'install permissions'` shows the five permissions `granted=true`; S-03 steps 3–4 run here too.
7. **Relock**, only after step 6 passes: `adb reboot bootloader`, `fastboot flashing lock` (confirm on the phone; **WIPES Phone B again**), boot. Pass: yellow boot screen with the owner key's ID; `getprop ro.boot.verifiedbootstate` = `yellow`, `ro.boot.flash.locked` = `1`. Leave OEM unlocking **on**.
8. **Update path** (M4-IMG-03): rebuild with a changed overlay against the same build, `adb reboot sideload` (or `adb reboot recovery`, then "Apply update from ADB"), `adb sideload "$vos_ota"`, and check it boots locked with data intact. Do not sideload again until the snapshot merge from the previous update has finished (`adb logcat -s update_engine`).

The same recipe builds for `akita` (post-1.0 port, decision 40): `--device akita` with the akita OTA.

## Pass criteria
Boots locked (yellow state, owner key); all five permissions granted (`dumpsys package`); a second same-key OTA with a rebuilt overlay sideloads and boots locked with data intact.

## Fallback
Tier F with zero patches (§4.6 a); open the Tier F epic the same day; M1 continues on Tier S.

## Result: desk build PASS, flash PENDING (2026-10-19; rebuilt 2026-10-20)
`image/build.sh` v0 built a VOS Image from `panther-ota_update-2026101601.zip` (the build Phone B runs) with throwaway test keys in the agent's scratch space (never `~/.vos-keys`), in about 40 s on the workstation, with no root. Rebuilt 2026-10-20 after the PR review fixes, with the hello APK as a signed release build (throwaway key, not debuggable):
- Input verified against `image/pins/grapheneos-ota-panther.crt`.
- Graphene's `product` is ext4 with `shared_blocks` (deduplicated, read-only) and 909 free blocks (3.6 MB), 42 free inodes. The script grows the raw image by the overlay size + 64 MB (`resize2fs`), unshares (`e2fsck -E unshare_blocks`; only 297 blocks were shared), adds the overlay with `debugfs` (root:root, 0755/0644, `u:object_r:system_file:s0`, the AOSP 2009-01-01 timestamp on all four inode times and in the superblock), reads every file back and checks each added inode's owner, mode, label and times, requires a clean `e2fsck -fn`, and rebuilds the hash tree and FEC with `avbroot avb pack --recompute-size`.
- `avbroot ota patch --rootless --replace product` re-signed vbmeta and the OTA; the output passed `avbroot ota verify` against the test OTA cert and AVB key, and its `product` is byte-identical to the built one. `product` grew from 1,250,050,048 to 1,318,981,632 bytes (super headroom: S-02).
- Reproducible: two builds of the same overlay from the same OTA and keys, a minute apart, gave byte-identical `product` images and byte-identical output OTAs (SHA-256 `fd2daee7…` with the test keys).
- Inode limit: the grow is smaller than one block group, so the inode count stays at 1280 and the overlay can add at most ~39 files and dirs. Enough for the hello image and the first real overlay; a bigger overlay needs `resize2fs` to a size that adds a block group, or `mke2fs` rebuild (open item for `image/build.sh` v1).

**Correction to the plan's permission list:** `CONCURRENT_AUDIO_RECORD_BYPASS` (§6.0 S-01 claim in this file, S-31) does not exist on Android 17. Phone B lists `android.permission.BYPASS_CONCURRENT_RECORD_AUDIO_RESTRICTION` (`signature|privileged`); the hello APK and allowlist use that name. Read on Phone B 2026-10-19: `MODIFY_AUDIO_ROUTING`, `CAPTURE_AUDIO_OUTPUT`, `CAPTURE_MEDIA_OUTPUT`, `CAPTURE_VOICE_COMMUNICATION_OUTPUT` and `CAPTURE_AUDIO_HOTWORD` are `signature|privileged|role`; `MEDIA_CONTENT_CONTROL` is `signature|privileged`; `DEVICE_POWER` is `signature|role|module` (not grantable to a product priv-app; matters for S-36).
